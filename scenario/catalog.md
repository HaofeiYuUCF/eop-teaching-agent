# Teaching case catalog

Read this catalog during intake after the supplied lecture and learning needs. Load only the
selected case's detailed resources. Cases support learning objectives; they do not determine them.

## Recommend with lecturer override

1. Honor an explicit case choice, including a supplied new case or no case. Do not substitute a
   case because another is easier. Explain any essential evidence/tool gap and adapt within the
   objective, or ask about the specific blocked decision.
2. Without a choice, identify which case best supports the actual lecture objectives. Then assess
   entry capabilities, teachable prerequisites, time, permitted tools and usable evidence. A
   discipline or course level alone never establishes ability. Real-data requirements can make
   either case unsuitable; do not silently replace required observations with synthetic data.
3. Recommend one case in a sentence explaining its fit and limitations. Include it in the lecture
   plan for the lecturer to override at the existing plan review. Do not add a case approval gate.
4. If the cases remain equally useful, ask one preference question offering both with their
   different learning applications. If unanswered, use a provisional recommendation based on
   the lecture's main worked example; if still tied, provisionally use I-4 for continuity with
   earlier packages. State this assumption in the plan, which still requires normal acceptance.
5. If neither fits, say why and offer another supplied context or `scenario: null`. Do not force
   a transport project into an unrelated lesson. A two-case comparison is used only when requested
   or accepted as part of the lesson's objectives and time budget.

Record selected case path/revision, mode, rationale and source-date context using the
[plan schema](../reference/blueprint-schema.md). Recommended defaults are not instructor acceptance.

## Compatibility and changes

An older plan's explicit scenario stays selected; missing selection metadata does not trigger a
new interview. For old `scenario: null` plans, retain no case unless adaptation is requested.
When adapting to a new lecture or audience, reassess fit. A case change invalidates affected
case-dependent inputs, activities, assessments, exports and review results. Revise and recheck
those artifacts; retain acceptance of unchanged decisions under the
[shared policy](../reference/workflow-policy.md).
